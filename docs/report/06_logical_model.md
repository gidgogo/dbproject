## 6.1 모델링 범위

구현 범위 다섯 화면에 필요한 데이터를 기준으로 엔터티를 정했다.

| 화면 | 필요한 데이터 | 엔터티 |
|---|---|---|
| 경기 결과 | 스코어보드, 박스스코어, 기타 기록, 심판 | 경기, 팀경기기록, 이닝득점, 타자경기기록, 타석, 투수경기기록, 경기기타기록, 경기심판 |
| 선수 프로필 | 개인정보, 시즌별 기록 표, 선수 비교 | 선수, 선수시즌소속, 선수연봉, 시즌기록_공식 (경기 적재 후 집계 뷰도 사용) |
| 팀 프로필 | 시즌별 팀명·홈구장, 상대전적 | 팀, 팀시즌, 구장 |
| 순위 | 시즌 순위, 게임차, 최근 10경기 | 팀순위_공식 (경기 적재 후 팀경기기록 집계와 비교) |
| 통계 시각화 | 공식 시즌 기록 비교·팀 순위. 경기 적재 후 타구 방향·백분위 | 시즌기록_공식, 팀순위_공식, 타석결과코드 |

KBO 공식 시즌 기록·순위는 현재 화면에서 직접 조회한다. 경기 기록을 확보하면 별도 집계 뷰와 비교한다.
공식 값과 직접 집계 값은 출처를 표시해 구분하며, 경기 데이터가 없는 상태를 시즌 기록 0으로 표시하지 않는다.
네이버 투구 정보는 제외했고, 수비·주루 전용 시즌 기록과 등록·말소 이력은 아직 구현하지 않았다.

| 출처 | 수집 방법 | 들어가는 엔터티 |
|---|---|---|
| KBO 게임센터 박스스코어 | kbodata | 경기·팀경기기록·이닝득점·타자경기기록·타석·투수경기기록·경기기타기록·심판 |
| KBO 기록실·선수 상세 | 직접 크롤링 (data-pipeline/crawl/) | 선수·선수시즌소속·선수연봉·시즌기록_공식·팀순위_공식 |
| 직접 입력 | data/reference/*.csv | 팀·팀시즌·구장·타석결과코드/유형·기타기록유형 |

## 6.2 엔터티 정의

| 엔터티 (물리명) | 정의 | 주식별자 | 식별자 종류 |
|---|---|---|---|
| 팀 (team) | KBO 구단. 팀명이 바뀌어도 같은 구단이면 하나 | 팀ID | 외부 코드(KBO 팀코드) |
| 팀시즌 (team_season) | 시즌별 팀명·약칭·홈구장 | 팀ID + 시즌 | 복합(식별 관계) |
| 구장 (stadium) | 야구장 | 구장ID | 인조 식별자 |
| 선수 (player) | 선수 마스터 | 선수ID | 외부 코드(KBO playerId) |
| 선수시즌소속 (player_season) | 선수가 어느 시즌에 어느 팀 기록을 남겼는가 | 선수ID + 시즌 + 팀ID | 복합 |
| 선수연봉 (player_salary) | 시즌별 연봉 | 선수ID + 시즌 | 복합 |
| 경기 (match) | 한 경기 | 경기ID | 외부 코드(kbodata/KBO 경기 ID) |
| 팀경기기록 (match_team) | 경기 스코어보드의 팀별 한 줄 (R·H·E·B·승패) | 경기ID + 팀ID | 복합 |
| 이닝득점 (inning_score) | 팀의 이닝별 득점 | 경기ID + 팀ID + 이닝 | 복합 |
| 타자경기기록 (batter_match) | 박스스코어 타자 한 줄 | 경기ID + 선수ID | 복합 |
| 타석 (plate_appearance) | 타자의 타석 하나 | 경기ID + 선수ID + 이닝 + 이닝내순번 | 복합 |
| 타석결과코드 (pa_result_code) | 좌중안·유땅 같은 결과 표기 | 결과코드 | 외부 코드(kbodata) |
| 타석결과유형 (pa_result_type) | 안타·2루타·땅볼 등 유형과 집계 규칙 | 결과유형코드 | 코드 |
| 투수경기기록 (pitcher_match) | 박스스코어 투수 한 줄 | 경기ID + 선수ID | 복합 |
| 경기기타기록 (match_event) | 결승타·홈런·도루·실책 등 | 기록ID | 인조 식별자 |
| 기타기록유형 (match_event_type) | 기타 기록 항목 | 기록유형 | 코드 |
| 심판 (umpire) / 경기심판 (match_umpire) | 심판, 경기-심판 M:N 해소 | 심판ID / 경기ID + 심판ID | 인조 / 복합 |
| 시즌타자기록_공식, 시즌투수기록_공식 | KBO 기록실 시즌 누적 값 | 선수ID + 시즌 + 팀ID | 복합 |
| 팀순위_공식 (team_rank_official) | KBO 기록실 기준일별 순위 | 시즌 + 팀ID + 기준일 | 복합 |

### 현재 프로필과 과거 시즌 구분

`player.current_team_name`, `current_uniform_no`, `profile_source_url`, `profile_crawled_at`은
현재 프로필 원문과 조회 시점을 나타낸다. 상무 같은 리그 밖 소속도 보존하며 팀 FK를 강제하지 않는다.
`player_season`은 기록실의 해당 시즌 팀 표기만 저장한다. 현재 등번호를 과거 시즌에 복사하지 않는다.
`player_salary.season`은 크롤러에 지정한 연봉 기준 연도이며 과거 연봉 복원 결과가 아니다.

## 6.3 관계와 카디널리티

표기: `1` 정확히 하나, `0..1` 선택, `0..N` 0개 이상, `1..N` 1개 이상. "식별"은 부모 키가 자식의 PK에 들어가는 관계다.

| 부모 | 자식 | 부모 쪽 | 자식 쪽 | 식별 여부 | 의미 |
|---|---|---|---|---|---|
| 팀 | 팀시즌 | 1 | 0..N | 식별 | 팀은 시즌마다 이름·홈구장을 가진다 |
| 구장 | 팀시즌 | 0..1 | 0..N | 비식별 | 시즌 홈구장 (모를 수 있음) |
| 팀시즌 | 경기 (홈/원정 2개 관계) | 1 | 0..N | 비식별 | 경기의 두 팀은 그 시즌에 존재하는 팀이어야 함 |
| 구장 | 경기 | 0..1 | 0..N | 비식별 | 경기 장소 |
| 경기 | 팀경기기록 | 1 | **정확히 2** | 식별 | 적재 커밋 전에 2행 검사. 트리거는 홈·원정 일치 검사, 검증 뷰는 직접 수정으로 생긴 누락도 탐지 |
| 팀 | 팀경기기록 | 1 | 0..N | 식별 | |
| 팀경기기록 | 이닝득점 | 1 | 0..N | 식별 | 공격한 이닝만 행이 있음 |
| 팀경기기록 | 타자경기기록 / 투수경기기록 | 1 | 0..N | 비식별 | 출전 선수의 소속 팀이 그 경기 두 팀 중 하나임을 보장 |
| 선수 | 타자경기기록 / 투수경기기록 | 1 | 0..N | 식별 | |
| 타자경기기록 | 타석 | 1 | 0..N | 식별 | 대주자처럼 타석이 없는 출전도 있음 |
| 타석결과코드 | 타석 | 1 | 0..N | 비식별 | |
| 타석결과유형 | 타석결과코드 | 1 | 1..N | 비식별 | |
| 경기 | 경기기타기록 | 1 | 0..N | 비식별 | 인조 식별자 사용 |
| 선수 | 경기기타기록 | 0..1 | 0..N | 비식별 | 이름 매핑 실패 시 NULL |
| 경기 ↔ 심판 | 경기심판 | 1 / 1 | 0..N / 0..N | 식별 | M:N을 연관 엔터티로 해소 |
| 선수 ↔ 팀시즌 | 선수시즌소속 | 1 / 1 | 0..N / 0..N | 식별 | 선수와 팀시즌의 M:N (이적하면 한 시즌에 두 팀) |
| 선수 | 선수연봉 | 1 | 0..N | 식별 | |
| 선수, 팀시즌 | 시즌기록_공식 | 1 | 0..N | 식별 | |
| 팀시즌 | 팀순위_공식 | 1 | 0..N | 식별 | |

## 6.4 주식별자 선정 (7장 식별자)

### 선수: 이름 대신 KBO playerId

| 후보 | 유일성 | 불변성 | 판단 |
|---|---|---|---|
| 선수명 | ✗ 동명이인 (같은 시즌·같은 팀에도 있을 수 있음) | ✗ 개명 | 탈락 |
| 선수명 + 생년월일 | △ 이론상 겹칠 수 있음, 박스스코어엔 생년월일이 없음 | △ | 탈락 |
| 선수명 + 팀 + 시즌 | ✗ 같은 팀 동명이인 | ✗ | 매핑 키로만 사용 |
| **KBO playerId** | ✓ KBO가 부여 | ✓ 이적·개명해도 유지 | **채택** |

kbodata는 선수를 이름으로만 구분하므로, 기록실에서 `시즌·팀·이름 → playerId` 매핑표(선수시즌소속)를 먼저 만들고
박스스코어 이름을 playerId로 바꾼 뒤 저장한다(`data-pipeline/etl/player_mapper.py`). 같은 팀·같은 시즌 동명이인은
① 타자/투수 구분, ② 선수별 출전 일자(Daily 페이지), ③ 사람이 확인한 예외표 순으로 해결한다.

### 경기: kbodata 경기 id (`20250601_OBWO0`)

- kbodata CSV의 `idx`(날짜+더블헤더+**팀번호**)는 같은 경기라도 팀마다 값이 달라 경기 식별자가 될 수 없다.
- raw JSON의 `id` = 날짜 + 원정팀코드 + 홈팀코드 + 더블헤더 번호 → 경기마다 유일. KBO 게임센터 `G_ID`
  (밑줄 없음)로 변환되어 KBO 게임센터 기록과 연결된다.
- 단점: 날짜·팀을 이어 붙인 **지능형 키**라 속성과 어긋날 위험이 있다. → `ck_match_id_parts` CHECK로
  경기ID와 (경기일자, 원정팀, 홈팀, 더블헤더) 가 항상 일치하도록 했고, KBO G_ID는 생성 컬럼으로 만들었다.

### 팀: KBO 팀코드 (OB, SK, WO …)

팀명은 바뀐다(SK 와이번스 → SSG 랜더스, 넥센 → 키움). KBO는 구단명이 바뀌어도 팀코드를 유지하므로
팀코드를 주식별자로 쓰고, 시즌별 팀명은 팀시즌 엔터티로 분리했다.

### 인조 식별자를 쓴 곳

구장(공식 코드 없음), 심판(원본에 이름만 있음), 경기기타기록(자연키가 길고 원문 파싱 결과에 의존) —
경기기타기록은 (경기ID, 기록유형, 순번)을 UNIQUE 대체키로 함께 둔다.

### 물리 모델에서 추가한 대리키 (7장)

위 표의 **복합 주식별자는 논리 모델의 식별자**다. 물리 모델(Flyway `V1__init_schema.sql`)에서는 팀 백엔드(JPA)가
엔터티마다 단일 `@Id`를 쓰도록, 복합 식별자 테이블에 대리키 `id`(bigint, 자동 증가)를 PK로 추가하고
복합 식별자는 `UNIQUE`(`uq_<표>_key`)로 그대로 강제했다. 업무 규칙과 FK(복합 업무키 참조)는 바뀌지 않는다.
논리 ERD(`erd/erd_logical.mmd`)는 업무키를 식별자로 그리고, 테이블 기술서(10장)는 `id` PK + 업무키 UQ로 적는다.

## 6.5 정규화 과정 (10주차)

kbodata가 주는 타자 기록 표를 출발점으로 삼았다. (값은 설명용 예시)

### 원본 (비정규형)

`batter.csv` — idx · name · team · position · i_1 … i_18 · hit · bat_num · hit_get · own_get

| idx | name | team | position | i_1 | i_2 | … | i_5 | … | hit | bat_num |
|---|---|---|---|---|---|---|---|---|---|---|
| 20250101001 | 가상타자A | 두산 | 8 | 1019 | - | … | 10137000 | … | 2 | 4 |

문제점
1. **반복 그룹**: `i_1 ~ i_18` 같은 의미의 컬럼이 18개 반복 → 이닝이 19회가 되면 컬럼을 추가해야 하고,
   "4회에 친 안타"를 찾으려면 18개 컬럼을 모두 뒤져야 한다.
2. **원자값 위반**: 한 이닝에 두 번 타석에 서면 `10137000`(1013 우안 + 7000 1비)처럼 한 칸에 값 두 개가 들어간다.
3. **식별자 문제**: `idx`는 팀마다 달라 경기를 식별하지 못하고, 선수는 이름으로만 구분된다.

### 1NF — 반복 그룹·다중값 제거

이닝 칸 하나를 행 하나로 바꾸고, 한 칸의 여러 결과는 `이닝내순번`으로 나눈다.

`타석_1NF`(**경기ID, 선수ID, 이닝, 이닝내순번**, 팀ID, 포지션, 타수, 안타, 타점, 득점, 결과코드, 결과명, 결과유형, 타수포함여부, 루타수)

### 2NF — 부분 함수 종속 제거

PK가 (경기ID, 선수ID, 이닝, 이닝내순번)인데
- 팀ID·포지션·타수·안타·타점·득점은 **(경기ID, 선수ID)** 에만 종속 → **타자경기기록**으로 분리
- 같은 원리로 경기일자·구장·관중은 경기ID에만 종속 → **경기**로 분리

`타자경기기록`(**경기ID, 선수ID**, 팀ID, 라인업순서, 포지션, 타수, 안타, 타점, 득점)
`타석_2NF`(**경기ID, 선수ID, 이닝, 이닝내순번**, 결과코드, 결과명, 결과유형, 타수포함여부, 루타수)

또 다른 2NF 사례: 선수시즌소속(**선수ID, 시즌, 팀ID**)에 연봉을 두면, 연봉은 팀과 상관없이 (선수ID, 시즌)에만
종속된다(시즌 중 이적해도 연봉은 하나). → **선수연봉**(선수ID, 시즌)으로 분리.

### 3NF — 이행 함수 종속 제거

`타석_2NF`에서 결과코드 → 결과명·결과유형, 결과유형 → 타수포함여부·루타수 (이행 종속)
→ **타석결과코드**(결과코드, 결과명, 결과유형, 수비위치, 타구방향), **타석결과유형**(결과유형, 타수포함여부, 안타여부, 루타수 …)로 분리하고
`타석`(**경기ID, 선수ID, 이닝, 이닝내순번**, 결과코드)만 남긴다.

다른 3NF 사례: 팀시즌(팀ID, 시즌) → 홈구장ID → 구장명·지역 → 구장명은 **구장**으로 분리.

### 정규화 결과로 얻은 것

- 타율·출루율·장타율을 **타석 결과 코드표의 플래그만으로** 계산할 수 있다(뷰 `v_batter_match_line`).
  예: 희생플라이(타수 아님)를 실수로 타수에 넣는 규칙 오류가 코드표 한 곳에서만 관리된다.
- 박스스코어의 타수·안타(타자경기기록)와 타석 결과로 센 타수·안타를 비교해 변환 오류를 찾는 검증이 가능하다
  (`v_check_batter_pa`).

## 6.6 유도 속성과 의도적 중복 (7장 유도 속성)

| 속성 | 처리 | 이유 |
|---|---|---|
| 시즌 타율·출루율·OPS, 시즌 투수 ERA, 팀 순위·게임차 | 일반 테이블에 중복 저장하지 않고 뷰/MV로 계산 | 일반 뷰는 조회 때 계산. MV는 결과를 저장하므로 적재·수정 후 `fn_refresh_stats()` 호출 필요 |
| 기록실 공식 시즌 기록·순위 | 저장 (별도 `_official` 테이블) | 현재 시즌 표·순위 화면의 직접 조회 원본. 경기 집계 확보 후 검증 기준으로도 사용 |
| 경기.시즌 | 생성 컬럼 (경기일자에서 계산, 직접 입력 불가) | 시즌별 조회가 많아 인덱스가 필요 → 저장하되 불일치 불가능 |
| 경기.KBO경기ID | 생성 컬럼 | KBO 게임센터 연동 키 |
| 투수 선발 여부 | 저장 안 함 → 등판순서 = 1 | 원본(kbodata `mound`)과 등판순서가 다르면 변환 단계에서 경고 |
| 팀경기기록.홈원정구분 | **저장 (의도적 중복)** | 경기의 홈팀ID로 유도 가능하지만 거의 모든 조회에 필요 → 저장하고 트리거로 경기와의 일치를 강제 |

저장한 유도 값이 원본과 어긋나는지 보는 검증 뷰(`v_check_*`, `v_compare_*`)를 함께 두었다
(보고서 7장 7.6 참고).
